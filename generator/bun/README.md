# Приоритет выбора API и библиотек в Bun-проектах

## Основной принцип

Для обеспечения максимальной производительности, совместимости и минимального размера зависимостей мы придерживаемся строгого порядка выбора инструментов.

---

### 1. **Bun Native API — ПРИОРИТЕТ №1**

* **Всегда** в первую очередь проверяйте встроенное API Bun.
* **Почему:** Bun предоставляет высокооптимизированные, нативные реализации для множества задач (файловая система, HTTP-сервер, парсинг env, скрипты и т.д.). Это быстрее и не требует установки дополнительных пакетов.
* **Примеры:**
  * `Bun.file()` вместо `fs.readFile` или `fs-extra`.
  * `Bun.serve()` вместо `express` или `http.createServer` для простых серверов.
  * `Bun.password` для хеширования/верификации.
  * `Bun.build()` для сборки.
  * `Bun.$` для выполнения shell-команд.

### 2. **Node.js Native API — ПРИОРИТЕТ №2**

* Если нужная функциональность **отсутствует в API Bun**, используйте встроенный API Node.js.
* **Почему:** Bun поддерживает большинство модулей Node.js (`fs`, `path`, `crypto`, `child_process` и т.д.). Это стандартно и надежно.
* **Пример:** Для сложных операций с потоками (`stream`) или криптографии, которых нет в Bun, используйте `node:crypto` или `node:stream`.

### 3. **Сторонние npm-пакеты — ПРИОРИТЕТ №3 (использовать с осторожностью)**

* К сторонним библиотекам следует прибегать **только если**:
  * Нужной функциональности нет ни в Bun, ни в Node.js API.
  * Требуется очень специфичная, сложная логика (например, ORM, валидация сложных схем, специализированные форматы).
  * Пакет является *де-факто* стандартом и критически важен для бизнес-логики (например, `axios` для сложных HTTP-клиентов, `lodash-es` для утилит, если это действительно необходимо).
* **Почему осторожно?** Каждая зависимость увеличивает размер проекта, может привносить уязвимости, замедлять установку и иногда конфликтовать с экосистемой Bun.

---

## Краткая памятка для принятия решений

```
Нужно решить задачу Х.
1.  ➡️ Есть ли для этого встроенный метод/модуль в Bun (Bun.*)?
    │   Да -> Использовать его. ✅
    │   Нет -> Перейти к шагу 2.
    ↓
2.  ➡️ Есть ли для этого стандартный модуль Node.js (node:*)?
    │   Да -> Использовать его. ✅
    │   Нет -> Перейти к шагу 3.
    ↓
3.  ➡️ Рассмотреть сторонний пакет.
    │   Перед установкой спроси:
    │   - Это последнее разумное решение? 
    │   - Нет ли более легкой альтернативы?
    │   - Активен ли пакет и хорошо ли поддерживается?
    │   Да на все -> Установить и использовать. ⚠️ (с пометкой)
```

## Пример кода с комментарием по правилу

```javascript
// ПРАВИЛО: Bun API > Node.js API > Сторонние пакеты

// ✅ ХОРОШО (Приоритет 1): Используем нативный Bun API
const file = Bun.file('package.json');
const data = await file.json();

// ✅ ХОРОШО (Приоритет 2): Нет аналога в Bun, используем Node.js API
import { createHash } from 'node:crypto';
const hash = createHash('sha256').update('data').digest('hex');

// ⚠️ ДОПУСТИМО (Приоритет 3): Сложная валидация, используем проверенную библиотеку
import { z } from 'zod'; // Обоснование: Нет в Bun/Node, стандарт для валидации схем.
const schema = z.object({ name: z.string() });
```

**Итог:** Следуя этому правилу, мы строим эффективные, быстрые и современные приложения, максимально используя преимущества Bun, не отказываясь при этом от всей экосистемы JavaScript, когда это действительно необходимо.
